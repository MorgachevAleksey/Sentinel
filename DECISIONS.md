## Проблемы/решения
Проблема: задать четкие границы разработки\архитектуры - не создаваьб огромную платформу с нуля когда уже есть готовые библиотеки, одновременно с этим написать полностью ручную реализацию приложения для демонстрации навыков и практической пользы
Решение: выделить контуры, использовать паттерн разработки "Стратегия":
- Подключения (песочница и боевой контур) - один адаптер (разные url\токены\флаги)
- Стратегия торговли - две стратегии: покупка при просадке по дневным свечам и вторая стратегия-заглушка для демонстрации масштабируемости
- Исполнение - фактически тот же адптер

Проблема: реализация 12 factor app, для 3ех конфигураций запуска: по-умолчнию, для разработки, для прода
Решение: идеоматичесное - 3 иерархичных YAML - материнский с dev по умолчанию и дочерние dev, prod

Проблема: нужна кастомная ин-ция по состоянию проекта, а отдельный эндпоинт с контроллером health не идеоматично
Решение: переделать эндпоинт heath на индикатор для актуатора

Мысль на будущее: устроит ли меня offset пагинация для работы со свечами... (скорее всего придется перепиливать потом все на keyset)

Проблема: на этапе реализации клиента появилась мысль - оркестрирующий сервис MarketDataService может превратится в god-обьект. 
Я планировал создать отедельный сервис для работы с репозиторием и использовать его в MarketDataService - чтобы он отвечал исключительно за орекстрирование.
Но после того как я вынес маппер отдельным слоем - понадобился слой который будет его инжектировать и применять - и я не хотел бы что бы это был MarketDataService.
Решение: симетрично с CandleQueryService - создать тонкий адаптер-обработчик данных клиента перед MarketDataService и обозначит этот слой как "провайдер",
так же с прицелом на будущее масштабирование есть смысл реализовать его через интерфейс и реализацию интервейса

Проблема: MOEX отдает JSON свечей с указанным таймфреймом и датой начала до текущей (можно прокинуть till MOEXу через провайдер, если не до сегодняшнего) в формате columns[] data[][],
надо это замапить
Решение: изящное - 
1) составить хешмап с ключами колонок и содержимым в виде их индексов с нуля, получается карта индексов
2) пройтись по первому измерению двумерного data[][] и вызвать вспомогательную ф-ию, записывающую в результирующий лист
1) идея создания модели: по первому измернию data[][] вставить по индексу карты индексов

Мысль на будущее: возможно стоит сразу прописывать везде @Qualifier где потенциально может быть реализация интерфейса в нескольких бинах
